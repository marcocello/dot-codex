# Knowledge setup and ClickUp API

## Outcome

When a Second Brain capture or review lacks configuration/default, the harness invokes knowledge-config in the same task, asks for missing selection, persists the user's chosen default and resumes the original requested operation after resolution succeeds. It does not just tell the user to run setup or fabricate a default. Unrelated coding tasks and explicit standalone Markdown/Zotero capture do not trigger setup. An explicit none profile is configured, not missing.

The single integration skill knowledge-config owns all setup, profile resolution, provider references and direct API scripts. Capture and review retain their purpose and consume that integration skill. Existing shared resolver path remains a thin compatibility launcher; existing version-1 MCP, Markdown and none profiles remain valid and overrides do not change defaults. Existing profile verification, classification, deduplication and read-back rules remain. No actual account/default is chosen or external content mutated by implementing/testing this feature.

## CLI and configuration

- Canonical resolver: skills/knowledge-config/scripts/knowledge_profile.py. Existing scripts/knowledge_profile.py delegates without duplicate logic. Existing put/default/list/resolve behavior remains. Missing file/default raises exit 3 and a JSON stderr object with code SETUP_REQUIRED and skill knowledge-config; invalid files/unknown explicit profiles remain errors, not setup or fallback.
- ClickUp profiles accept optional transport=mcp|api (omission remains mcp). API requires exactly one token_env (environment variable name) or token_file (absolute private file path), optional auth_type=personal|oauth (default personal), and the existing connection/account/workspace_id/tasks/deals/ideas routing. API account is the numeric authenticated ClickUp user ID; workspace and destination IDs are numeric. No token value is saved or printed. Secrets are read only by the client from the explicitly selected reference; no auto-discovery of old token files. Token files must be regular, nonsymlink, owner-only-readable files, never created by setup. Users provide secrets privately outside chat/config.
- put adds --transport, --token-env, --token-file, --auth-type. Version 1 remains because fields are optional extensions. Invalid combinations fail without changing the saved config.
- API entrypoint skills/knowledge-config/scripts/clickup_api.py; global --config PATH and --profile NAME precede command. Missing config/default uses same SETUP_REQUIRED. A non-ClickUp/API profile fails before reading a credential or networking.
- `discover --token-env NAME|--token-file PATH [--auth-type personal|oauth] [--workspace-id ID]` works before configuration, returns authenticated user identity and accessible workspace identities. An explicitly selected workspace additionally returns its active spaces/folders/lists for setup. This is metadata discovery, never default selection.
- `check` validates authenticated user ID, authorized workspace and each configured list's space membership in that workspace; returns verified=true and profile/account/workspace/list identities only after all checks. Shared lists for multiple record kinds are rejected by direct API until a discriminator is implemented (MCP preserves existing mapping policy).
- `fields KIND` returns verified list metadata/statuses and accessible custom-field definitions. `list KIND` retrieves pages starting at 0, includes closed tasks, subtasks and tasks in multiple lists, covers archived false and true, deduplicates by task ID, and returns tasks with complete=true only after all pages succeed. Pagination follows last_page when present, otherwise stops on empty page; repeated pages or excessive pages error, never return a partial list as complete. KIND is tasks|deals|ideas.
- `get KIND TASK_ID` and update/custom field commands restrict targets to the selected configured list and workspace. A foreign task must not be mutated. Task reads verify returned team_id and list.id against the configured scope. Multi-list records whose home list differs may appear in scoped list results but cannot be mutated via the direct client without a verified home-list scope.
- `create KIND --data-file PATH` consumes a JSON object with supported fields name, description OR markdown_content, status, priority, due_date, due_date_time. Name required; data types and status/priority validated before write; enforce check_required_custom_fields=true. Read-before-create semantic matching remains the invoking skill's responsibility. `update KIND TASK_ID --data-file PATH` supports the same fields but requires a nonempty patch, preserves omitted fields and checks membership first. No arbitrary endpoint/payload pass-through, deletion, notification/comment send, schema mutation or automatic connector installation.
- `set-field KIND TASK_ID --field-id ID --value-file PATH` uses ClickUp's custom-field endpoint for URL, short_text/text, email/phone, number/currency, checkbox and drop_down fields after verifying field ID/type and allowed dropdown option IDs from the list schema. Unsupported/ambiguous field types fail before mutation; values are JSON. Regular create/update reject custom_fields instead of silently losing them.
- Mutation output has verified=true only after GET read-back verifies task identity, workspace/list and requested values; fields require read-back value equality (normalizing numeric representations where API uses strings). Failed/uncertain writes or failed read-back raise explicit errors with known task ID, no automatic write retries and no success receipt. User may inspect the ID before any retry. No automatic MCP/API fallback: transport choice persists and may be explicitly changed within the same verified account.

## Transport and failure boundaries

Production HTTPS endpoint is fixed to https://api.clickup.com/api/v2. Requests have a finite timeout; redirects are refused to prevent forwarding auth. URL segments are validated/quoted. No credential is accepted on CLI arguments or emitted in errors; response/error bodies are not dumped on failure. Account mismatch stops before workspace/list content access; inaccessible workspace or foreign lists stop before task access. HTTP 401/403, 429 (report rate limit), malformed responses, timeout and missing credentials return actionable bounded errors without blind retries. Direct API can overcome connector availability/operation limitations but not ClickUp permissions or plan limits.

## Verification

Independent proof exercises actual public CLI activation and durable configuration, mocking only the unsafe external HTTP edge and synthetic credentials. It must observe outgoing paths, account checks, auth selection and mutation payloads, persisted fake-service state and GET read-back. Cover API/MCP isolation, identity/workspace/list/task mismatches, pagination beyond first page, create/update/custom-field read-back, missing credentials, 401/403/429, malformed responses, uncertain writes/read-back failures and no retries/leaks. Semantic assessment covers missing-config ask/save/resume, none, invalid configuration and preserved standalone capture behavior. Live SaaS success remains unverified without user-selected credentials/account; do not request credentials in chat or claim a live connection.
