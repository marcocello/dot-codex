# Independent proof: knowledge capture consolidation

## Done

The agreed 44-entry inventory exposes one knowledge-capture entrypoint with three substantive destination modes. Supplied input and explicitly requested external gathering share the Second Brain process. Retired entrypoints/callers are absent, prior consolidated skills and separate interaction/Notion helpers remain unchanged, Zotero resources are byte-preserved, and the relocated RIS CLI produces correct offline artifacts. Independent scenario inspection confirms routing, uncertainty, deduplication, permissions and read-back guidance against the candidate text.

## Command

Run `"${CODEX_HOME:-$HOME/.codex}/scripts/proof_run_capture.py" --feature-dir docs/features/knowledge-capture-consolidation --timeout-seconds 120 --note "knowledge capture discovery, instructions and offline helper"`. Dedicated runner: `proof/run.sh`; selected test: `proof/acceptance.py`. Gate, metadata validators and affected regressions remain separate.

## Environment and target

Producer: the approved capture consolidation in FEATURE.md and original user corrections. Real inputs: preimplementation inventory snapshot, protected resource hashes, current SKILL.md/metadata/references, and source-capture JSON supplied to the relocated RIS CLI. Authority: skills.toml for membership, installed owned skill instructions for destination and mode routing, and unchanged helper scripts for artifact generation. Primary consumer: fresh local skill discovery; affected consumers: harness callers and the Zotero import artifact boundary. Python 3.11+ and local files suffice.

No live Notion or Zotero operations are activated. The offline helper runs as a subprocess with temporary JSON input and RIS output read-back. No fake replaces the helper; the unsafe external connector session is not invoked because live external capture is outside the accepted target. The most plausible central breaks are a hidden old capture entrypoint, wrong destination authority, four wrappers instead of a combined workflow, duplicate-creation guidance under incomplete reads, or a broken relocated helper/resource.

## Dedicated scenarios

1. **Inventory/discovery/preservation:** acceptance.py compares retained 47-entry baseline with the agreed 44-entry set, requires unchanged other declarations, absent four retired folders, valid new frontmatter/UI metadata, and no retired current references. Relative Markdown links are resolved through real files. Historical feature evidence and dated reviews are excluded. Protected content includes the inventory engine, previous four consolidated skill packages, separate interaction-history tool and Notion adapter. Both Zotero Python helpers and note-shapes.md must remain byte-identical under the new package; filenames are discovered rather than prescribing reference organization.
2. **Relocated helper activation:** acceptance.py executes build_capture_ris.py via its public --spec/--out CLI for a video and article fixture, reads the actual RIS, and verifies complete expected type/title/creator/date/publisher/canonical URL/tags/source-note/terminator output. A Highlights-first input must fail and produce no RIS for each type. Only temporary local files are written. This catches lost helper paths and invalid source-note embedding without external writes.
3. **Destination/Markdown:** frozen scenarios.json gives ambiguous note, bare URL, explicit Markdown destination, daily-note append with uncertainty/privacy and missing-convention cases. An independent full read-through must show one destination decision, relevant-only mode loading, no accidental sweep/cross-destination write, preserved collection conventions, local capture dates and actual read-back before a private receipt.
4. **Common Second Brain process:** fixed supplied-note and scoped-weekly-sweep cases must converge on one substantive classify/deduplicate/write/verify mode. Existing-row, shared-title, incomplete-read, unsupported-adapter and indirect commercial-progress cases require conservative matching, supported operations, exact manual proposals and no invented state or blind create. Existing schema/values and read-back remain intact.
5. **Research/integrated routing:** fixed machine-transcript, inaccessible article, existing canonical item without writer, and expired session cases require companion readiness, target selection, canonical deduplication, provenance/access limits, exact separate child notes, precomputed metadata, one session/tag preservation, stop without reimport, and parent/child read-back. Interaction-history capture must remain separate and explicit.

Semantic results are written by `/root/proof_author` to `evidence/semantic-review.json` after reading the final candidate entrypoint and all mode/resources it routes to. Every fixed group needs a grounded PASS/FAIL, citations and reasoning. acceptance.py binds that evidence to hashes of current live routing and relocated resources and fails on missing or stale evidence. The implementer cannot write its own semantic PASS.

## Proves

The real local discovery/inventory interface, readable instruction routing and independently assessed document outcomes, byte-preservation of helper behavior, and concrete offline CLI artifact generation. A removed central entrypoint or lost resource fails automatically; contradictory required capture guidance fails the independent scenario read-through. The semantic assessment is not inferred from words merely appearing in files.

## Does not prove

An agent consistently obeys the text across live probabilistic executions, remote accounts are configured, external writes succeed, transcripts were fetched, or the active app refreshed discovery. Existing Notion adapter placeholders remain known limitations; verifying it is unchanged does not establish operational readiness.

## False-green risks and known gaps

Semantic inspection can miss ambiguity and cannot substitute for an external capture run. Hash binding detects stale evidence, not adversarial writer manipulation. The distinct final reviewer remains required. Metadata structure and current source-link checks supplement, rather than replace, repository validators. Exact external operation support must be checked when actual capture is requested; no credentials or live endpoints are part of these fixtures.
