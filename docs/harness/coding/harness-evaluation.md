# Evaluating harness changes

Use for consequential changes to discovery, execution, completion, or recovery. Routine formatting and product work do not need a harness evaluation campaign.

## Choose The Owner

Start with an actual failure or a demonstrated gap. Decide whether it belongs to product context, domain technique, skill routing, a tool contract, capture, or runtime enforcement. Repeated failure after a wording change is a reason to reconsider ownership, not automatically add another paragraph.

In existing change evidence, record the motivating case, expected improvement, likely regression, and an unseen check. Prefer a small comparison to a new manifest system. Retain the previous instructions so a change can be reversed without discarding unrelated work.

## Observe Behavior

Give a fresh worker the realistic request, minimum raw repository context, and the instructions being evaluated. Withhold the intended answer, diagnosis, and rubric. Observe actual investigation, questions, tool actions, artifacts, and verification. When conversational behavior matters, continue with realistic user answers and observe whether the agent revises its understanding. A question-only trial does not establish the rest of that exchange.

Include pressure in both directions: uncertain product work needing substantive discovery, and clear authorized work that should proceed with justified choices. Check whether the agent incorporates real answers, distinguishes advisory questions from consequential user decisions, and waits only on dependent work when authority or a necessary decision is missing. Include visual refreshes that should preserve existing behavior without inventing a redesign decision, and access changes that must not be assumed. Check direct specification/implementation requests and narrow slices in existing systems as well as new projects. Do not reveal the expected decision in the task prompt. The evaluator needs expectations; the task worker does not.

For product dialogue, observe whether early questions explore direction and the user's work, and whether answers lead to autonomous decisions and narrow outcomes rather than serial questions about fields, screens, or storage. Existing code should inform feasibility without silently shrinking ambition. Check that discovery and initial specification/proof design do not start a native Goal; implementation owns that transition. Do not claim runtime Goal enforcement from a trial that disables those tools.

For comparisons, hold model, tools, fixtures, task context, and authorization steady where possible. Record unavoidable differences, actual skill versions loaded, and whether selection was forced rather than automatic. Preserve failures and interruptions. Repeat trials when variance or the consequence warrants it; a single sample demonstrates possibility, not a success rate.

Judge consequential missed decisions, unnecessary questions/pauses, scope expansion, accepted-outcome coverage, false completion, and rework. Measure time/cost only when captured comparably. Do not optimize question count, word count, artifact count, or an evaluator's confidence as substitutes for outcomes.

## Match The Claim To The Evidence

- Structural validation proves parsable metadata, references, and command contracts.
- Retained hashes show which inputs and observations were preserved; they do not re-execute an agent.
- Scenario judgments calibrate a decision in supplied context; they do not prove repository investigation or delivery.
- Fresh agent trials show observed actions on those tasks and instructions.
- Executable application proof establishes its named behavioral boundary, not universal agent reliability.

The evaluator applies the withheld rubric to actual traces/artifacts, including counter-evidence. Accept, revise, or reject the change based on those observations. Keep a limitation when an important boundary could not be exercised; do not relabel a narrower check to fill the gap.
