# Proactive outcome discovery proof

## Done and target

The five current instruction files support the accepted practical outcome: infer intent, inspect missing ordinary states, propose evidence-grounded choices, ask consequential questions, carry cases into independent proof, and reject incomplete delivery despite scoped green tests. Target is source instruction consumption, not a deployed application or universal future model behavior.

## Command

Run `docs/features/proactive-outcome-discovery/proof/run.sh`; official attempts use shared `proof_run_capture.py`. Python 3 and Bash are required. The runner does not mutate acceptance or implementation and invokes no other feature proof.

## Scenarios and boundary

`proof/cases.json` defines six dedicated cases: the motivating fresh-team null vision default, first-use notifications, paid/destructive backup fallback, bounded validation repair, analysis-only import explanation, and a passing-test delivery with a missing visible result. Each supplies a concrete request, context facts, and expected outcome. A distinct agent receives only raw requests/facts and current instruction paths, without expectations, and produces concrete responses retained in `evidence/blind-responses.json`. The proof author independently judges these responses against the frozen cases. These are response exercises, not fabricated observations from the original project.

Producer is the user request and scenario facts. Activation is reading current AGENTS routing, relevant Shape/Ship procedure and proof boundary, with README as north star. Consumer is an agent choosing a concrete response and subsequent work. Read-back is the blind response and independent author’s interpretation, practical decision questions, instruction evidence and limitations for each scenario. No external services, paid actions or fake application layer are used. Central defects caught include copying an empty default, re-asking implementation permission, inventing consequential fallback policy, asking a universal questionnaire, expanding analytical scope, and calling omitted behavior complete.

`proof/check.py` verifies frozen acceptance, unchanged previous feature files/scripts/inventory, current five-file Markdown link/anchor navigation, complete independently authored semantic assessment, and exact candidate hashes. The independent author writes `evidence/semantic-assessment.json` after reading the candidate, including each case’s concrete response and reasoned verdict plus cross-cutting invariant review. The runner checks evidence identity/completeness/freshness; it does not judge semantics using keywords. The invariant review covers owner-specific concise additions, preserved routing/default Goals/no renewed approval, permissions/scope, fixed acceptance/independent proof, and no new guide or universal questionnaire.

## Proves and limits

This establishes independent reasoned source-level scenario coverage and unchanged protected inputs. It does not establish actual app fixes, unprompted behavior outside these bounded exercises, deterministic compliance, deployment or runtime availability. Assessor bias or missed semantics remains possible; the separate final reviewer must inspect the actual instructions and evidence. Hashes are freshness evidence, not security isolation. Inline link checking does not cover arbitrary prose paths.

## Evidence and frozen inputs

Retain baseline files, baseline red, candidate assessment, official capture and final review separately. Gate and other regression verification remain separate from acceptance. No prior feature proof is rerun as this feature's acceptance.
