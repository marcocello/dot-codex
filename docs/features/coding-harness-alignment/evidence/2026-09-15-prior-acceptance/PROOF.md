# Coding harness alignment proof

## Done

The installed checkout exposes one coding lifecycle owner and useful coding capabilities, resolves active local instruction links, and has no retired lifecycle entrypoints or duplicate core/proof guidance. Real supporting commands preserve feature ownership, reject unsupported completion, retain execution failures, and detect the proof-input mutations they actually guard. Independent agents exercise the changed instructions on six realistic decision cases and retain an assessed, candidate-bound transcript.

## Command and target

Run `docs/features/coding-harness-alignment/proof/run.sh` from this checkout. Official attempts use the shared `scripts/proof_run_capture` with this feature directory, a caller-selected timeout, and a meaningful note. The runner invokes only this feature's dedicated standard-library acceptance program; the repository gate and generic tests are separate regression checks.

The target is the authored instruction/inventory tree and shared commands in the current checkout. Inventory discovery uses the real inventory CLI and installed skill files, not the running task's cached catalog. A later fresh Codex task must load this tree to use the revised instructions; this proof cannot replace runtime-owned skill loading.

No product API or network is faked. Temporary application files are explicit fixtures for the real shared command consumer boundary; they do not pretend to be agent behavior. Temporary repositories and subprocesses are cleaned up.

## Independent exercise protocol

1. After implementation, generate a candidate snapshot with `python3 docs/features/coding-harness-alignment/proof/acceptance.py snapshot`. Save its JSON output outside the fixed proof inputs, normally beneath `proof/runs/`.
2. Give a fresh agent the six `prompt` fields in `proof/cases.json`, the checkout path, and permission to read current instructions. Request concrete next actions and completion decisions. Do not give it the acceptance rubrics or this proof's expected answers. Retain the full exercise prompt and responses in a UTF-8 transcript with the agent's actual identity/history reference. This is a bounded decision exercise; it must not mutate product code or pretend to execute scenarios.
3. A different assessor reads the retained transcript, current candidate and frozen rubrics, then writes a report under `proof/runs/` using `proof/assessment-schema.json` as the contract. Every case needs a reasoned PASS or FINDINGS; missing information cannot be invented. An assessor may be the original independent proof author. The final delivery reviewer remains a fresh, separate read-only role.
4. Supply the report with `HARNESS_ALIGNMENT_ASSESSMENT=/absolute/path/to/report.json` when running proof. Transcript paths are relative to the report directory; reports and transcripts are outputs, not acceptance inputs. No default fabricated report, skip flag, model API loop, or fallback assessment exists.

The report binds the full candidate snapshot, transcript digest, actual identities/history references, and all six assessed results. The executable verifies structure and binding; a separate assessor owns semantic judgment. Self-reported identities and PASS labels are not cryptographic attestations. The parent and final reviewer must compare them with actual agent execution records.

## Meaningful failure and limits

Authoring began after limited preliminary domain-skill edits; those edits were paused. Root/workflow instructions and duplicate guidance still represented the previous lifecycle when this proof was written. A pre-alignment attempt must retain the duplicate-guidance failure and missing independent evidence, rather than claiming every test was red before any edit.

This proof establishes discoverability, selected real command behavior, reference integrity, and observed decisions for six cases. It does not establish universal future agent compliance, end-to-end execution of arbitrary future features, hard Goal stopping, automatic complete conversation capture, runtime permission enforcement, or protection against an implementer able to rewrite the entire checkout. Those are runtime boundaries or explicitly documented limits of this migration. No benchmark, word-presence test, review opinion, or existing generic suite substitutes for these scenarios.
