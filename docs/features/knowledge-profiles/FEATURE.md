# Persistent knowledge profiles

## Outcome and target

One harness can persist a default Second Brain profile independently of its reusable skills. Capture and review select that profile on each invocation, including a new process/chat. Profiles support Notion, ClickUp, repository Markdown, and explicitly disabled persistence (`none`). This is a local harness convention, not a native Codex setting. The consumption target is the checked-out harness CLI and skill instructions; live SaaS operations are not configured or exercised by this change.

## Decisions and journeys

- Store version 1 TOML in `${CODEX_HOME:-$HOME/.codex}/knowledge.toml`, outside tracked shared defaults. Never infer a default from installed connectors or a single account. Missing configuration returns an actionable setup requirement and does not create files.
- Public CLI is `scripts/knowledge_profile.py`: `put NAME --provider PROVIDER` with provider-specific `--connection`, `--account`, `--workspace-id`, `--tasks`, `--deals`, `--ideas`, `--root`; optional `--default` explicitly saves a default; `default NAME` explicitly changes it; `resolve [--profile NAME]` resolves one profile; `list` reports configured profiles. Global `--config PATH` allows isolated testing/explicit harness configuration. Remote profiles require connection, account, workspace and all three destination IDs. Markdown requires an absolute root; none requires no destination. No credentials belong in this file.
- An explicit per-operation profile wins over the default without changing persisted settings. An explicit session selection is passed as the same override until changed. All-profile review requires an explicit request, enumerates configured profiles, and keeps source identities separate. Remote resources are addressed by configured IDs, not display names.
- `put` replaces one complete named profile and preserves all other profiles and the current default unless `--default` is supplied. Invalid input/configuration, unknown profiles, unsupported versions/providers, placeholder identifiers, and invalid paths fail without mutation or provider access. Configuration writes are atomic and coordinated to avoid lost updates.
- An unavailable connection, identity mismatch, unsupported operation, or invalid configuration never redirects to another account/provider or to Markdown. Return the blocker and exact unsaved proposal when possible. Resolution establishes routing only; connectors must verify identity, workspace membership, schema and operation capability before content access/writes.
- Missing first-use selection asks for destination/profile details once when a knowledge operation is requested. A complete user request to configure a default authorizes saving it. Merely using a profile does not authorize changing the default. No real account is selected during this implementation.
- Generic capture retains classification, complete matching before creation, conservative commercial changes, source evidence, scoped source gathering and read-back after writes. Review is read-only, defaults to one configured profile, and retains brief/weekly behavior. Direct Markdown notes and Zotero archival remain explicit separate capture modes.
- Provider references define Notion database/property mapping, ClickUp list/custom-field mapping and capability discovery, Markdown stable record IDs and paths with read/match/update/read-back, and none as no reads/writes. Remote adapters are connector-based instruction adapters, not new REST clients. No installations, remote schema creation, synchronization, auto-commit or pushes are part of this feature.
- Rename `knowledge-notion-review` to `knowledge-review`, update inventory and active references. Add `knowledge-config` for profile setup. Keep `knowledge-notion-api` provider-specific, but disable its legacy unconfigured CLI before network access with an explicit migration error; its fixed token, placeholder destinations and limited operations cannot meet profile identity guarantees. Usable Notion operations route through a verified connector. No silent legacy fallback.

## Verification boundary

Independent proof exercises real CLI configuration, reopening, override isolation, multiple account profiles, malformed/absent configuration, invalid writes, explicit none and Markdown routing. Semantic assessment of the actual skill/contract references verifies capture and review routing, unavailable-provider behavior, provider mapping and Markdown record lifecycle. Live authentication and SaaS read/write success remain unverified and are not claimed. Reusable profiles must not require repeating destination selection across chats.
