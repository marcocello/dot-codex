# ClickUp connections

Use the resolved account/workspace and the selected operation transport. MCP is the saved default when omitted; an explicitly approved API override may use the same profile’s saved credential without persisting a preference change.

## Capability and onboarding

Inspect actual MCP operations and identity binding. If absent, follow knowledge-tool-connect’s plugin discovery/installation flow. A connector label alone is not evidence of authenticated account identity. Pass explicit workspace/target IDs where supported and verify existing field types/options before writes. Follow the user’s requested organization; do not create default lists, statuses or categories.

The bundled API supports identity/workspace discovery, list-based task operations, and v3 Docs/page operations below. Task/subtask deletion is supported. Comments, attachments, container deletion and schema changes are not implemented. An API token can support a transcript copy into an existing Doc; verify identity and the target before writing.

For supported API operations, first reuse a saved credential. If missing, ask whether the user already has a personal token. If not, guide them to ClickUp **Settings → ClickUp API → API tokens**, then generate a personal token using [official authentication guidance](https://developer.clickup.com/docs/authentication), then [token intake](credentials.md): accept a chat paste or guide private storage. User-operated token creation is separate from the API client. Existing OAuth tokens are supported; browser OAuth enrollment is not implemented.

MCP quota/rate-limit responses may justify offering API for supported operations after explicit user choice. API limits and permissions still apply. Reconcile any uncertain write before retrying; do not automatically switch or change the saved default.

## Direct API

All code is in this skill's `scripts/`. Run `"${CODEX_HOME:-$HOME/.codex}/skills/knowledge-tool-connect/scripts/clickup_api.py" --help`. Global `--config PATH`, `--profile NAME` and optional `--transport api` precede the command; the transport override changes no saved preference. The API resolves the same default as the workflows; `SETUP_REQUIRED` invokes setup and resumes rather than falling back.

For API profiles, `account` is the exact numeric ClickUp user ID, `workspace_id` is numeric, and task destinations are numeric list IDs; Docs commands use Doc/page IDs. No lists are required just to connect; legacy tasks/deals/ideas keys are optional aliases. `connection` is a descriptive identity for this credential binding, not an MCP tool selector. For API use, configure exactly one inline `token`, `token_env` or `token_file`, and `auth_type=personal` (default) or `oauth` for an existing OAuth access token. Store supplied tokens in private knowledge.toml through `credentials NAME --token-stdin`; never put them in shell command arguments, payload artifacts or version control. Chat intake follows [credential intake](credentials.md) and must never be echoed. Environment variables and absolute owner-only private token files remain supported alternatives. The API client itself never writes credentials. OAuth enrollment is outside this helper.

### Setup and operations

- `discover --token-env CLICKUP_WORK_TOKEN` (or `--token-file ABSOLUTE_PATH`) reads only the authenticated identity and authorized workspace metadata. `--workspace-id ID` additionally discovers that workspace's active spaces/folders/lists. Select with the user; do not infer a default from results. The credential reference is scoped by the user's setup choice before discovery.
- `check` verifies the account via `/user`, workspace authorization via `/team`, and any configured legacy list aliases through workspace space membership. With no aliases, check verifies only identity/workspace; each content operation verifies its selected list. Missing credentials, mismatched identity or inaccessible destinations block before task access. Success proves access at that moment, not future permissions.
- `fields DESTINATION` reads actual statuses and custom-field IDs/types. Use existing mappings; do not invent option IDs or create schema.
- `list DESTINATION` reads every accessible page, with closed tasks, subtasks, multi-list tasks and archived/unarchived coverage. Only a complete result may support matching. Completeness means all returned accessible pages, not access to private records hidden from the token. A later failed page yields an error, never a partial success.
- `get DESTINATION TASK_ID` reads an exact task. The direct client checks its workspace and home list before returning a verified record. Multi-list records with another home list may appear in list results but cannot be updated through the configured list; return that limitation instead of duplicating them.
- `create DESTINATION --data-file PATH` and `update DESTINATION TASK_ID --data-file PATH` accept JSON containing only name, description OR markdown_content, status, priority (1–4 or null), due_date (epoch milliseconds or null), due_date_time (boolean). Create requires name and enforces ClickUp required custom fields. Required custom fields that cannot be satisfied by this core payload can block creation; do not bypass them. Update sends only supplied fields; when changing descriptions, merge with the freshly read content to preserve unrelated evidence. Read-back must verify requested values. If ClickUp omits a requested control such as due_date_time from GET, the write is honestly reported unverified, not retried.
- `set-field DESTINATION TASK_ID --field-id ID --value-file PATH` consumes a JSON scalar. It verifies field applicability and supports text, URL, email, phone, numeric/currency, checkbox and dropdown option IDs. Other types return an explicit unsupported-capability error. A custom-field update is separate from ordinary update; never send custom_fields in a core patch.

The invoking workflow owns semantic matching before create; the API cannot deduce that two differently worded tasks are duplicates. Read-back failures and uncertain requests return a known task ID when available and no automatic mutation retry. Inspect the ID or complete candidate set before any deliberate retry. HTTP authorization failures, rate limits, provider plan restrictions and inaccessible private tasks remain limits of direct API access. No container or Docs/page deletion, comments/messages or schema changes are implemented; creating a Doc requires explicit visibility and applicable user authorization.

### Sources

The transport follows official [authentication](https://developer.clickup.com/docs/authentication), [task pagination](https://developer.clickup.com/reference/gettasks), [task creation](https://developer.clickup.com/reference/createtask), [partial updates](https://developer.clickup.com/reference/updatetask), and [custom-field](https://developer.clickup.com/docs/customfields) contracts. Live credentials and SaaS state require separate verification for the selected account.

DESTINATION is an explicit numeric list ID or a configured legacy alias. A saved destination may be a URL for another tool; validate its resource type before choosing a task command. Operations inspect only their selected list; they do not require unrelated mappings.

## Docs and pages (v3)

The [official v3 OpenAPI specification](https://developer.clickup.com/openapi/ClickUp_PUBLIC_API_V3.yaml) defines workspace-scoped Docs endpoints. The helper keeps v2 identity/task requests and v3 Docs requests on the fixed ClickUp host. Docs commands verify account/workspace without requiring legacy list aliases.

- `docs-search`: fetch all cursor pages of accessible, non-deleted workspace Docs. Search locally by name; the endpoint has no keyword parameter. Completeness covers only returned accessible Docs.
- `doc-get DOC_ID`: fetch and verify Doc metadata and workspace.
- `pages-list DOC_ID`: retrieve the complete nested page listing with `max_page_depth=-1`.
- `pages-get DOC_ID [--content-format text/md|text/plain]`: retrieve the nested page tree with content.
- `page-get DOC_ID PAGE_ID [--content-format text/md|text/plain]`: read one page and verify its Doc/workspace.
- `page-create DOC_ID --data-file PATH`: JSON fields `name`, optional `parent_page_id`, `sub_title`, `content`, and `content_format` (`text/md` or `text/plain`). A supplied parent must be a verified page in this Doc. Omit it for a root page.
- `page-update DOC_ID PAGE_ID --data-file PATH`: JSON fields `name`, `sub_title`, `content`, `content_format`, and `content_edit_mode` (`replace`, `append`, `prepend`). Edit only requested values. Protected pages are rejected. A replacement must preserve unrelated content; append/prepend verifies the resulting content against a fresh pre-write read.
- `doc-create --data-file PATH`: JSON `name`, explicit `visibility` (`PUBLIC`, `PRIVATE`, `PERSONAL`, `HIDDEN`), optional `create_page` and `parent` (`id`, numeric `type`: Space 4, Folder 5, List 6, Everything 7, Workspace 12). Container membership is checked before writing; Everything/Workspace parent IDs must equal the selected workspace. Omitted parent uses the provider's workspace default. Doc read-back exposes only `public`, so the result reports exact visibility as unverified; do not retry a successful creation to resolve that gap.

For a transcript copy, list existing pages first to detect a prior copy and locate the requested parent; preserve supplied text and metadata in a new child page. Build the JSON file directly from the source file using a JSON library rather than shell interpolation. Use `text/plain` for verbatim text. The client separately reads the created page and compares the requested fields, including its parent and full content. Markdown export may normalize content or omit rich elements; a mismatch is reported unverified, never treated as success or automatically retried. Retain the returned resource ID and inspect it before any deliberate retry. No transcript is sent to unrelated lists or Docs.

## Delete a task or subtask

Use `delete DESTINATION TASK_ID` only when the user has requested deletion of that concrete task. Resolve ambiguous names to exact identities first; existing explicit authorization does not need to be requested again. A request to implement deletion support alone does not authorize deleting real objects. Confirm that the intended action is deletion of the task, including its contained content, rather than removal from an additional List or merely closing it. Do not expand a selected subtask into its parent or a set of matching tasks.

The command checks account, workspace, selected home List and task identity before one `DELETE /api/v2/task/{task_id}` request. It then reads the same task again. Success means the scoped DELETE succeeded and the follow-up GET returned HTTP 404; it does not claim permanent erasure from backups or Trash. A preflight 404 is an error, not evidence this command deleted anything. A still-readable task, denied access, rate limit, timeout or malformed response leaves the deletion unverified. Report the task ID and uncertainty and inspect before any deliberate retry; never automatically repeat a DELETE or switch transports after an uncertain mutation.

With MCP, discover an actual delete-task capability and apply the same target, authorization and read-back checks. The [official delete-task endpoint](https://developer.clickup.com/reference/deletetask) also applies to subtasks; [MCP supported tools](https://developer.clickup.com/docs/mcp-tools) lists task/subtask deletion. The public [API endpoint index](https://developer.clickup.com/llms.txt), checked 2026-09-20, lists no Doc/page deletion endpoint. For Docs/pages, explain that missing capability before requesting a token: use a genuinely available connector deletion capability if exposed, otherwise guide deletion of the selected resource in ClickUp's UI. Do not invent an endpoint, erase page content as a substitute, or claim that a token unlocks unsupported deletion. Other object deletion requires a separately implemented, scoped adapter.
