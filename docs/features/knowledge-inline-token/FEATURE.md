# Inline API token storage

User explicitly wants the token stored in knowledge.toml with connection settings.

Support a string token field in remote profiles, mutually exclusive with token_env/token_file. Keep version 1, old reference bindings, preferred transport and other profile behavior. API clients use inline credentials through shared credential loading; internal resolver returns usable raw config but public CLI output recursively replaces token values with "[redacted]". Errors must not include token values. Validate nonempty printable ASCII token with no whitespace and bounded 16 KiB length.

Public CLI credentials NAME --token-stdin reads the token from stdin (not argv), validates and saves inline, replacing old token/reference binding without changing other fields/profiles/default/transport. Strip trailing/leading whitespace from input to allow a terminal newline; reject invalid/oversized input. credentials NAME --import-current privately loads the selected existing token_env/token_file/inline credential and replaces its binding with token, retaining auth_type unless explicitly changed. No token-reading discovery outside the selected profile. Both options mutually exclusive with reference options. No --token VALUE argument. Legacy commands remain compatible and redacted when showing inline config.

Atomic config writes use mode 0600. Reads of inline-token config require an owner-owned regular file without group/world permissions; reject symlink/special-file and unsafe inline permissions before API use. Reference-only legacy configs retain compatible mode handling. No token is printed by list/resolve/credentials/default/transport/put; old shared/legacy launchers inherit behavior. Add harness-root knowledge.toml/lock ignore entries, preserving existing ignore work. Documentation permits inline private local config (including ignored harness-local config) but never tracked/version-controlled credentials. No migration that deletes original credential files or rotates tokens.

Update setup/provider/token guidance: inline token is the requested default storage; chat token is accepted without echo and supplied through suitable secret-input/stdin tooling or structured private write when available, never literal shell arguments. Interactive user can run a hidden getpass prompt and pipe into credentials --token-stdin; if tooling unavailable state exact blocker. Existing reference alternatives remain supported. State plaintext/owner-only storage fact once, no repeated permission ceremony. Config output redaction is not a valid source for rewriting token values.

Inspect current harness configuration metadata without exposing values. If configured references exist, migrate them with import-current under existing user authorization and verify readback/mode without exposing tokens; don't delete source files. If no config/credentials exist, report that no actual token was migrated, without inventing a token/account.

Independent proof: public subprocess CLI persists token/readback TOML with synthetic value, mode0600, redacted output on commands, multiple-profile/default preservation, conflict/invalid/unsafe permission rejection, reference migration, API consumption (HTTP edge fake) with no emitted token. Compatibility regressions and independent final semantic/security review. No live SaaS mutation.
