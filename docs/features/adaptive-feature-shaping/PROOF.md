# Adaptive Feature Shaping Proof

## Done
- Product input of any maturity and cardinality routes through adaptive app/feature shaping rather than fixed app-only or feature-only assumptions.
- Materially incomplete product intent can trigger one recommended grouped question round even when a safe default exists; resolved or reversible details do not trigger ceremonial questions.
- Artifact creation is conditional, and adjacent discoveries are classified without automatically expanding durable artifacts or implementation scope.
- Feature and proof artifacts remain lean, decision-owned, and separated from implementation authorization.
- Proof authoring selects pressure from the feature-specific risk model.
- Existing safe-default, complete accepted-feature preparation, queue, feature-size, and implementation-authorization invariants remain compatible with adaptive shaping.
- Undeclared legacy Codex skill links cannot bypass the canonical global intake router; their external source directories remain out of scope and untouched.

## Command

```bash
"${CODEX_HOME:-$HOME/.codex}/scripts/proof_run_capture" --feature-dir docs/features/adaptive-feature-shaping --timeout-seconds 60 --note "verify adaptive conversational shaping and risk-based proof"
```

## Scenario: Intake and artifact selection adapt to the request
- Producer/activation: pytest reads the global routing kernel, app shaping, feature shaping, and both real UI prompts.
- Consumer: a user starting from a rough or detailed app idea, one feature, or several ideas.
- Read-back: assertions require maturity-neutral intake, conditional app/architecture artifacts, one package per accepted independently provable outcome, and no mandatory bulk artifact generation.
- Fake: none.
- Catches: routing all rough input to app generation, treating detailed input as implementation-ready without challenge, or always creating app/architecture/spec documents.

## Scenario: Conversation crystallizes decisions without specification slop
- Producer/activation: pytest reads feature and app discovery policy.
- Consumer: the user deciding product purpose, benefit, behavior, and material tradeoffs before implementation.
- Read-back: assertions require understood-purpose and recommendation summaries, one grouped shaping round for materially different plausible outcomes, recommended defaults with consequences, and lean durable artifact rules.
- Fake: none.
- Catches: forbidding useful questions whenever a safe default exists, including equivalent “ask and wait only when no safe recommended default exists” wording; serial one-question turns; approval ceremonies; and dumping exploration into durable specs.

## Scenario: Adjacent discovery improves architecture without automatic scope growth
- Producer/activation: pytest reads feature/app shaping and global scope policy.
- Consumer: a single-feature request that exposes a prerequisite, likely follow-up, alternative, or unrelated idea.
- Read-back: assertions require explicit classification, accepted-decision control over artifact and implementation expansion, and bounded architecture seams for plausible follow-ups.
- Fake: none.
- Catches: implementing every adjacent idea, silently omitting a required prerequisite, or ignoring a foreseeable ownership seam that causes immediate rework.

## Scenario: Proof pressure targets real failure modes
- Producer/activation: pytest reads proof authoring and harness rationale.
- Consumer: the proof decision following feature shaping.
- Read-back: assertions require selection from a feature-specific risk model rather than universal happy-path or operational checklists.
- Fake: none.
- Catches: happy-path-only proof and mechanically applying every operational pressure to every feature.

## Scenario: Existing preparation and authorization guarantees remain compatible
- Producer/activation: pytest runs the existing greenfield-default, lean-completion, artifact-authority, and feature-size contract suites against the changed instruction surfaces.
- Consumer: existing app preparation and contract-authoring flows.
- Read-back: assertions preserve safe-default inference for smaller/reversible decisions, preparation of every accepted feature and executable proof, lean feature cohesion, and the separate explicit implementation-authorization boundary while accepting the new material shaping-question policy.
- Fake: none.
- Catches: reverting useful defaults, silently skipping an accepted feature package, authorizing implementation from discovery answers, or leaving the repository gate red behind a narrow feature proof.

## Scenario: Legacy public entry paths cannot bypass canonical shaping
- Producer/activation: pytest enumerates the repository skill paths that previously exposed `app-to-features` and `feature` as implicitly invocable alternatives.
- Consumer: future Codex app and feature shaping requests.
- Read-back: assertions require those undeclared legacy links to be absent while canonical owned skills and prompts remain available.
- Fake: none.
- Catches: selecting the old fixed 3–7 feature generator, mandatory `APP.md`, foundation-first ordering, Gherkin-only feature output, or missing executable proof package.

## Scope
Proves:
- The active harness instruction surface encodes adaptive conversational shaping, conditional artifacts, bounded adjacent-feature discovery, and risk-based proof.

Does not prove:
- Deterministic compliance or product judgment by every future model.
- That every future repository exposes enough evidence to resolve product questions locally.
- The quality of external research or live provider behavior.

False-green risks:
- Static policy assertions cannot guarantee future adherence or good judgment.
- Required phrases could exist without influencing a future run; fresh preflight, realistic proof, and evaluation remain necessary safeguards.
- The selected compatibility suites do not replace the repository gate; the gate remains required for this dot-codex change.

Evidence method:
- deterministic

Known gaps:
- Live shaping quality remains probabilistic and should be improved from future interaction evidence.

## Environment
- Repository-local Python and pytest.
- No network, credentials, external mutation, or product implementation.
