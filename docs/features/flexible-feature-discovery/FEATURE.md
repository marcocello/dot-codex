# Flexible discovery and narrow feature slices

## Outcome

The coding harness investigates and discusses consequential unknowns before turning an idea into accepted specifications, while carrying clear authorized work forward without a rigid sequence or unnecessary questions.

## Accepted behavior

- Sparring partnership is the default coding stance in greenfield and brownfield work, not a separate stage or an opt-in skill. Understand the surrounding user journey and architecture, challenge material weaknesses with reasons and stronger alternatives, and ask questions that improve the outcome. Scale effort to uncertainty and consequence; a tiny clear fix still receives judgment without automatic formal discovery.
- Shape explains its current understanding and recommendation, investigates discoverable facts, asks useful grouped questions, and revisits its understanding when answers reveal new material choices. It distinguishes accepted decisions, proposals, and assumptions. An answer resolves its own decision; announced interpretations do not become agreement.
- Prefer narrow independently demonstrable feature slices: one useful outcome, its necessary end-to-end path, and its proof. Split independently changeable outcomes, risky integrations, or unrelated policies; retain dependencies and a short whole-journey outline. Do not split into technical layers, drop required error cases, impose size quotas, or fully specify a large backlog before learning from the first slice.
- Discovery can remain conversation and bounded authorized investigation. Clear requests need no ritual question round. APP and ARCHITECTURE are created or extended when durable cross-feature context is useful, not as universal prerequisites. Accepted behavior is recorded before dependent implementation; speculative later slices stay provisional.
- Lifecycle skills describe responsibilities and acceptance boundaries rather than a compulsory sequence for every task. Preserve lightweight Fix, independent proof authorship and final review for material features, authorization, runtime ownership, accepted coverage, and the original delivery scope.
- Domain guidance preserves established contracts and uses architecture/starter defaults according to product fit. It does not require a dashboard starter for every UI, layers for every function, or explicit requests merely to preserve compatibility.
- Proof authors and reviewers can load concise role briefs and concrete boundary examples when useful. These explain how to catch incomplete implementations without mandatory example counts or additional approval stages.
- Harness evaluation uses actual task execution with raw context and withheld expectations where feasible. Distinguish structural checks, static retained assessments, simulated decisions, fresh agent runs, and demonstrated software behavior. Changes have motivating and unseen checks; no claim of reliability from a single successful sample.

## Verification and boundaries

An independent author prepares realistic isolated tasks and a rubric before implementation. Exercise candidate instructions with real tool use, including a broad request, an already-settled request, and a small repair. Include an unseen scenario and compare selected motivating cases with the pre-change instructions under comparable conditions. Record observed questions, artifacts/actions, unnecessary pauses, and limitations; do not test compliance by matching instruction wording. Final independent review covers coherent routing and retained safeguards.

No historical proof is rewritten to make this change pass. No new orchestration service, model change, deployment, external mutation, or automatic future monitoring is included.
