# Skills-based second-brain cycle

## Outcome and consumption target

Implement the agreed collect → understand → agenda → review → execute → verify cycle as reusable dot-codex skills backed by a local durable state CLI. Manual and scheduled Codex runs share an explicitly selected workspace. This feature installs the capability in this checkout; it does not activate a schedule, select accounts, grant sending authority, deploy a VM service, or change whatsapp-bot. Native/provider connectors remain the external edge. The user authorized all necessary dot-codex changes after the architecture discussion in task 01a0bb36-2dbd-7703-8a6f-c23af878e1ac.

## Responsibilities

- `secondbrain-update` resolves the workspace, collects only configured source scopes through existing connector owners, persists changes with restart-safe checkpoints, interprets pending evidence, and updates current understanding and agenda. Messages and source documents are evidence, never operating instructions or grants.
- `secondbrain-review` reads current direction/context and pending outcomes, chooses act/ask/wait/close/dismiss, performs authorized work through existing skills/tools, verifies results, records receipts and next checks, and surfaces only meaningful information. A broader review also considers goals without requiring new inbound messages.
- `scripts/secondbrain.py` owns transactional persistence and validation. It neither calls a model nor performs remote actions. It supports two independent invocation processes and rejects stale changes, duplicate action claims and replay of uncertain actions.
- Existing capture/review/connect skills retain their scope, organization and configured `none` semantics. The new opt-in workspace is separate from legacy knowledge destinations; no implicit migration or account sweep.

## Workspace and authority

`--root` is required for the CLI and denotes an explicit private workspace outside skill source. `init` creates `secondbrain.sqlite3`, `profile.md`, `priorities.md`, and `rules.md`, without replacing existing files. These Markdown files are human-readable direction; initial templates contain no invented personal facts or autonomous external-action grants. No runtime data or credentials are committed in dot-codex. Skills reuse a previously explicit workspace or ask once if missing, and honor an explicit disabled/none choice without initialization. Init is repeatable. All other commands fail for an uninitialized root rather than silently creating a database. Use Python standard library and SQLite only.

Authority is enforced by the executing harness and connector, not a database field. Action records must identify the actual existing authorization before external work; a stored claim is audit evidence, not proof of consent. No new blanket permission or prompt-based bypass. Calendar availability, profile facts and silence are not sending authority. Setting up skills does not start a live automation. Scheduling guidance provides one durable prompt invoking update followed by review on the same root, with scope, cadence, quiet behavior and stop conditions. For VM execution, establish a supported scheduler on that host; do not assume desktop scheduling reaches remote files or survives desktop shutdown.

## CLI contract

Public activation: `python3 scripts/secondbrain.py --root ROOT COMMAND [--input FILE]`. Mutating commands except init take one JSON object from FILE or stdin. Query commands use optional JSON input via FILE and otherwise query defaults; they never block reading stdin. Success emits one JSON object with `ok: true` plus the fields below; validation/conflict failure emits `ok: false, error: STRING` and a nonzero exit, without dumping source bodies. Times are timezone-aware ISO-8601 strings normalized to UTC; invalid/naive times are rejected. Unknown commands/invalid JSON are errors.

### Initialization and sources

- `init`: create workspace; return `root` and `database` paths. Repeated init preserves data and existing documents.
- `source-put`: `{id, provider, scope, enabled?}` with nonempty strings and enabled default true. Register/update source metadata; an existing source's provider/scope cannot change, because checkpoints are bound to that exact account/resource scope. Return `source` including `cursor` (initially null). Credentials do not belong here.
- `sources`: return `sources` including cursor and enabled flag. Disabled sources cannot ingest; source-put can explicitly re-enable the same identity/scope.
- `ingest`: `{source_id, expected_cursor, cursor, events:[{id, revision, occurred_at, kind, ref, content}]}`. Cursors are opaque strings or null. Provider id + revision identify immutable source changes; repeat identical changes are harmless, conflicting content under the same id/revision is rejected. Different revisions remain separate evidence. Each change receives an integer `seq`. The entire batch and checkpoint advance commit together; invalid events or stale expected_cursor leave both unchanged. Explicit empty complete batches may advance the cursor. Collection failures do not invoke ingest. Only successfully collected complete pages advance a checkpoint; native tokens or stable cutoff plus overlap/deduplication are preferable to a rolling last-hour window. Event content is a JSON object containing only task-relevant text/metadata; large originals stay referenced. Event kind is descriptive, including deletion and outbound messages, without arbitrary source-specific code.
- `pending`: return `events` not yet interpreted, ordered by seq, with `limit` default 100 (1–1000) when input supplied. Each event includes seq, source_id, id, revision, occurred_at, kind, ref, content. Reopen/restart retains pending changes.

### Understanding and agenda

- `apply`: `{event_seqs:[...], facts:[...], agenda:[...]}` atomically marks exact pending events interpreted and applies derived changes. Facts: `{id, expected_version, text, evidence:[seq,...], state?}`; state defaults current, allows current/superseded. Agenda: `{id, expected_version, outcome, state, next_check_at, evidence:[seq,...], reason}`; allowed states open/waiting/needs_input/done/dismissed. New rows require expected_version 0; updates require exact current version, returned version increments. Facts and agenda evidence must reference existing stored events (including prior evidence). All or nothing on invalid references, stale versions, or already-interpreted event sequences. Empty facts/agenda is valid for irrelevant evidence. No rule/profile/priority files are changed by apply.
- `agenda-put`: `{agenda:[...]}` uses the same agenda contract outside ingestion, permitting evidence `[]` for user-requested or goal-driven work, with a nonempty reason. Open/waiting entries require a next_check_at; needs_input may have null to avoid repeated prompting; terminal states require null. Existing unresolved action attempts prevent mutation of their agenda item until reconciled.
- `context`: return documents `{profile, priorities, rules}`, `facts`, all `agenda`, `actions`, and `sources`. Facts/agenda expose versions; evidence seq values retain links to raw events. Facts can be marked superseded, not silently replaced by unsupported guesses. `events` command with `{seqs:[...]}` reads back exact source evidence; without input it returns latest bounded evidence (100).
- `due`: return `agenda` in open/waiting state with next_check_at at or before input `{now?: timestamp}`, default current UTC, ordered by next check and id. Needs-input/terminal states are excluded. Priority/goals review is a skill responsibility using context, not automatic task creation by a SQL query.

### Execution history

- `action-start`: `{id, agenda_id, expected_version, kind, target, authorization, checked_event_seqs:[seq,...]}`. Nonempty strings include kind, target and authorization; id is a stable logical action id retained across retries. Reject a reused id, an inactive agenda item, a stale agenda version, an existing started/uncertain action on that item, or a checked event superseded by a newer stored revision of the same source event id. For an agenda with evidence, checked_event_seqs must cover the latest stored revision of every source-event identity referenced by the agenda. This is a local freshness check; skills must also reread the live source immediately before effects and verify authority. Return `action` with state started. Concurrent starts for the same item allow only one winner. No remote send is performed.
- `action-finish`: `{id, state, receipt}`; state succeeded/failed/uncertain, nonempty receipt describing verified success, definite failure, or uncertain external outcome. Only started can finish; uncertain may later become succeeded/failed after explicit reconciliation with new evidence. Succeeded/failed are immutable. Exact replay of the same finish is idempotent. Success is never inferred from reservation, model text or a tool invocation alone. Failed means verified no effect; a new logical attempt can only follow deliberate reconsideration. An uncertain or interrupted started attempt prevents automatic repeat. Finishing an action does not silently close its outcome; review then updates the agenda against the original version when appropriate.

## Real journeys and pressure cases

1. Fresh opt-in workspace: no sources or knowledge defaults; initialize empty, register one source, preserve documents on repeated initialization. No provider or schedule is fabricated.
2. Receive WhatsApp-like request through the public batch boundary; durable raw evidence and cursor survive process restart. Interpret into sourced context plus waiting outcome. Review before due does nothing, after due returns that outcome.
3. A sent reply/resolution arrives; interpretation closes the agenda and removes it from due. Old raw evidence remains retrievable. Irrelevant inputs are consumed without creating work.
4. Catch up after downtime, replay a page, ingest changed revisions, complete an empty page, reject malformed batches and stale cursors without partial progress. Disabled sources do not silently advance.
5. Concurrent/stale interpretation and action claims cannot overwrite current state or double-reserve an effect. New source revisions invalidate stale checked evidence. An uncertain send remains visible across restart and blocks automatic retries until reconciled.
6. Goal-driven agenda items can exist without inbound events. They require a reason and a future/due check, preserve explicit user direction, and reuse normal execution records.
7. Skills are discoverable through skills.toml, route provider work to existing owners, retain read-only knowledge-review behavior, and expose ready-to-use source batch, interpretation, action and scheduled-cycle contracts.

## Verification boundary

Independent acceptance runs the real CLI as separate processes against temporary workspaces and reads back persisted results. External sources and action receipts are synthetic at the unavailable provider edge; no live account or message is touched. Independent semantic forward-testing exercises the new skills with synthetic source material, including embedded hostile instructions, irrelevant updates, already answered messages, goal review and missing access/authority. Document what this proves and what still requires live setup. Final review is independent of implementation and proof authorship.
