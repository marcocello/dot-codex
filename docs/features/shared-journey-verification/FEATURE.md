# Shared journeys and implementation-round verification

## Outcome and authority

The user accepted replacing compulsory per-feature executable proofs with a feature inventory, acceptance criteria mapped to focused checks and shared end-to-end journeys, and verification at the end of a coherent implementation round. They authorized the harness changes in this task. Arbitrator's September 29 run motivates the change: duplicated setup, late obsolete UI interactions, and a narrow revocation check behind an expensive full suite. This change updates the reusable harness; it does not modify Arbitrator or claim its outstanding acceptance is complete.

## Accepted behavior

- Every feature retains an outcome and identifiable acceptance criteria. It may retain its existing FEATURE/PROOF/runner package or use FEATURE.md plus COVERAGE.json mapping every criterion to one or more shared verification packages. No placeholder feature runner is needed for mapped coverage. Shared packages contain PROOF.md and an executable proof/run.sh; focused API/CLI tests and browser journeys are both legitimate acceptance boundaries when they prove the mapped promise.
- Existing status schema, historical evidence, capture commands, and standalone proof completion remain supported. Add `implemented` for saved implementation awaiting round verification; it releases the active claim and has no completion pointer. One task still owns at most one actively edited feature. An implementation round groups related features without turning them into one large feature.
- A round review binds explicit features, their coverage mappings, all required passing check runs, selected regressions, target, source candidate, and distinct actual implementer/acceptance-author/reviewer attribution. Missing coverage, failed/unfinished newer checks, stale inputs, changed receipts, differing targets, or a completion owner mismatching the attributed review cannot support completion. Two features may reference the same check without copying or rerunning it. A subset of features may complete while independently blocked features remain unverified.
- Capture supports docs/verification/<check-id> packages without requiring FEATURE.md and optional explicit input scopes. Scope includes relevant source, shared dependencies, fixtures/configuration and the owning acceptance tree; broad repository capture remains the safe default. Relevant edits/additions/deletions invalidate scoped evidence. Unchanged independently scoped evidence can support a later round alongside a repaired check. Scope adequacy remains an independent review judgment, not dependency discovery or remote attestation.
- Round completion records a stable final candidate. Inventory reads retain historical completion without asserting current verification. A read-only current-round check reports stale coverage, changed candidate, changed evidence or newer failures. No missing integration is silently skipped or replaced by a fake.
- Guidance runs focused checks during implementation and relevant journeys at the end of a bounded round, with independently runnable expensive AI/visual/provider checks where practical. Rerun affected checks after repairs; broaden for shared-state or integration risk. Preserve independent acceptance and final review, failure records, privacy/concurrency negatives, actual consumer read-back, and external authorization boundaries.

## Validation and limits

Exercise real capture/status/receipt subprocesses in disposable repositories, plus retained legacy completion/capture regressions. Independently forward-test the instructions on a different small application task using raw context and withheld expectations. Assess coverage preservation, false completion, and unnecessary duplicated runners; do not claim an Arbitrator speedup without executing a comparable application round. No deployment, global install, external message or production run is part of this change.
