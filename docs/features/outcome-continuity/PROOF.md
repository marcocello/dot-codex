# Outcome continuity acceptance proof

Done means four isolated fresh-worker trials have retained raw tasks, instruction snapshots, visible action/result traces, and independently adjudicated outcomes. Candidate integration investigation, completion review, and authorized repair must satisfy the withheld semantic rubric. A passing baseline is valid; improvement is not required or inferred from this sample.

Command: `docs/features/outcome-continuity/proof/run.sh [retained-trials-directory]`. Default evidence location is `docs/features/outcome-continuity/evidence/trials`. Run only after actual trials and semantic adjudication. This executable checks artifact integrity and recorded judgments; it does not run agents, judge semantic behavior, or establish that a recorded identity is authentic. Final review of the harness change follows official capture and is separate from the trial adjudication required by this runner.

## Target and scenarios

The producer is a realistic raw user task with small local repository/provider files. Public activation is a fresh worker receiving that task and a supplied instruction bundle. The worker owns investigation/planning, a read-only review, or a local repair according to its request. The consumer is the user receiving a usable plan, justified completion verdict, or verified formatting fix. Read-back is the worker's actual visible tools/results and saved artifacts, adjudicated independently. The target is workflow behavior under forced instruction selection. There is no production service or unsafe external edge: the integration source is a synthetic but executable-shape vendor fixture, explicitly local and unavailable live. It is input evidence for investigation, not a fake replacing a claimed live integration test.

| Trial | Activation and read-back | Incomplete behavior caught |
| --- | --- | --- |
| Baseline integration | Raw integration task under preserved baseline bundle; inspect trace and FINDINGS.md | Docs-only plan that assumes authenticated download_path is customer-usable |
| Candidate integration | Identical raw task, fresh worker, candidate bundle; inspect source use and plan | Same assumption, or omission of the new-account create-to-download journey |
| Candidate review | Previously unseen presets request, application, passing tests; inspect trace and REVIEW.md | Accepting same-process tests despite promised close-and-reopen persistence |
| Candidate repair | Clear singular/plural bug; inspect resulting source and executed verification | Unnecessary questions/scaffolding or failure to repair and preserve plural behavior |

`proof/prepare.py` determines raw fixtures and REQUEST.md; `proof/rubric.md` determines semantic acceptance. `proof/check.py` and `proof/run.sh` determine retained-evidence validation. No per-heading or exact-word compliance tests stand in for behavior.

## Execution and retention

Create four fresh directories with `python3 proof/prepare.py integration /tmp/<unique-baseline>`, the same command with a different target for candidate integration, and cases `review` and `repair` for candidate controls. Paths are relative to this feature when invoking prepare.py this way. Supply the relevant instruction bundle separately. Worker prompt: “Work in <fixture>. Read REQUEST.md and carry it out using the supplied instruction bundle. Save the requested result there.” Do not supply FEATURE, PROOF, rubric, checker, expected answers, or another trial's result to workers. No worker spawns additional workers.

Retain each cell in its own directory named baseline-integration, candidate-integration, candidate-review, candidate-repair. Each contains original `fixture/` input files, `instructions/` snapshots, `trace.md` with visible prompt/commentary/tool calls/tool results/final (never private reasoning), `result.md` containing the returned findings/review or repair diff and verification, and `metadata.json` with worker_id, model, instruction_selection set to forced, source_session provenance, outcome (completed/failed/interrupted), and observation_kind (native-visible-trace or instrumented-tool-receipts). If child native traces are unavailable, retain actual commands and subprocess output captured during execution in tool-events.log, include dispatch prompt and returned result in trace.md, and record observation_limit explicitly. This fallback is instrumented tool-receipt observation, not a complete native trace; a retrospective worker narrative alone is insufficient. Hash tool-events.log as well. The adjudicator must inspect actual visible tool events or these execution receipts. Preserve final repair files separately from the original fixture. `inputs.json` maps retained file paths to SHA-256 hashes, including original fixture, instruction snapshot, trace.md and result.md. Hashes record retention, not runtime attestation.

A distinct adjudicator writes `adjudication.json` at the trials root with reviewer_id, limitations, comparison, and trials keyed by the four names. Each trial has a boolean pass, rationale, and evidence paths relative to that root (optional fragment after #). Record model_difference if models differ. Adjudication must reflect actual traces including adverse evidence; hashes and verdict schemas alone are insufficient acceptance. Keep failures and interruptions. Any additional attempt must be retained separately and its use explained without rewriting the initial comparison.

## Limits and false-green risks

One sample per cell is the smallest comparison that exercises the motivating discoverable provider ambiguity plus an unseen completion-review challenge and an autonomy control. It establishes observed candidate behavior on those tasks only, not improvement frequency or general reliability. Baseline and candidate integration use identical raw files, model/tools/authorization where possible, and disclosed unavoidable differences. Forced instruction loading cannot prove automatic skill routing. Discovery-only integration cannot prove implemented provider correctness, acceptance authorship in future tasks, native Goal enforcement, or live deployment. No claim about those boundaries is made.

The central false-green risk is an adjudicator approving a polished plan without investigating its trace or the consumer outcome. The withheld rubric demands sourced resolution and ordinary journey coverage, and the held-out review challenges a supplied test PASS directly. The integrity runner cannot eliminate evaluator error, identity spoofing, missing trace material, or variability. Independent final harness review must weigh the raw observations and narrow claims accordingly.
