# Second-brain configuration and native scheduling

## Outcome

`secondbrain.yaml` is the authoritative configuration for the private workspace, selected sources, initial intake window, and separate update/review cadences. The user chose native Codex scheduling and wacli for WhatsApp. Skills consume this file each run. Native schedule reconciliation uses the automation tool; YAML alone cannot change the app scheduler.

## Accepted boundary

Provide `scripts/secondbrain_config.py [--config PATH] show|sync-sources|schedule-plan`. Default config is `$CODEX_HOME/secondbrain.yaml`, falling back to `~/.codex/secondbrain.yaml`. Use safe YAML with duplicate/unknown-key rejection. Errors return JSON with ok=false, exit 1, without traceback/private values. A missing file never scans sources or creates a workspace. Resolve workspace and wacli store/repository paths relative to the configuration file, with home expansion. Do not resolve relative paths against the caller's working directory.

Schema version 1: `workspace` nonempty path; `initial_lookback_minutes` positive integer; `schedules.update` and `schedules.review`, each with `enabled` boolean and `every_minutes` positive integer; `sources` list of `{id, provider, enabled, scope}`. IDs are unique nonempty strings, provider one of whatsapp/repos/zotero/gmail/onedrive/clickup/notion. Scope is an object. Enabled sources require a nonempty explicit scope; disabled entries may have empty scope. WhatsApp scope uses `adapter: wacli`, `store` path, and `chats` list of explicit JIDs or the explicit choice `all`. Repos scope uses nonempty `paths` list. Other enabled providers require explicit scope but provider-specific validation remains connector-owned. No configuration field grants sending authority; rules.md and actual user/harness permissions retain ownership.

`show` is read-only and returns normalized configuration with absolute config/workspace/adapter paths. `sync-sources` validates the whole configuration first, initializes the selected workspace when needed, and atomically reconciles its source registry: additions and enabled toggles, preserving existing cursors; removed sources become disabled without deleting evidence. Existing provider or scope changes under the same ID fail the entire reconciliation, requiring a new source ID. Invalid configuration or scope conflict cannot partially change source registrations. Registry synchronization performs no remote collection.

`schedule-plan` is read-only and yields exactly two desired native heartbeat configurations with stable distinct names based on config path, separate intervals, ACTIVE/PAUSED according to enabled, and durable prompts referencing the absolute config and corresponding skill. Each run rereads configuration; disabled jobs stop. Prompts include safe action boundaries and quiet unchanged behavior. Changing only one interval affects that schedule only. Plan creation is not scheduler activation. Reconcile existing native automations using their actual IDs and current fields through automation_update, preserving notification preferences; never rewrite scheduler files or create duplicate schedules. An enabled schedule must have at least one enabled source for initial activation; a plan for enabled scheduling with no enabled sources fails clearly. Paused schedules may be prepared with unconfigured sources. Current default template has schedules paused at update 15/review 60 minutes and all sources disabled; no accounts are inferred. The private secondbrain.yaml is ignored; tracked secondbrain.template.yaml is copyable. Existing --root state CLI remains compatible.

## WhatsApp and runtime

Public response envelopes: `show` returns `{ok:true,config:{schema,config_path,workspace,initial_lookback_minutes,schedules,sources}}`; `sync-sources` returns `{ok:true,sources:[...]}` using the existing state CLI source shape; `schedule-plan` returns `{ok:true,schedules:[{name,kind:"heartbeat",status,rrule,prompt}]}` in update then review order. The YAML version field is `schema: 1`.

wacli is the chosen collection/execution surface, replacing whatsapp-bot in these skills. Keep `wacli sync --follow` separately supervised; no installation, QR pairing or daemon deployment is implied. Intake reads the selected store via read-only JSON CLI, both incoming and outgoing messages, bounded initial windows and durable complete checkpoints; never silently truncate a capped result. Explain historical/backfilled and edited/deleted coverage limitations, read-only SQLite option and reconciliation requirements. Revalidate live conversation and synchronization freshness before authorized replies; old local history cannot establish no reply. No live send is in this feature's proof or activation scope.

## Verification and limits

Disabled sources with an empty scope are unconfigured placeholders: synchronization does not register a new empty immutable scope. If their ID already exists, disable that registration while retaining its binding and cursor. This allows later first-time account selection without an artificial identity conflict. Nonempty configured scopes remain immutable even when disabled. WhatsApp `chats` is either the scalar `all` or a nonempty list of explicit JIDs.

Consumption target: local public configuration CLI, real SQLite registry readback through existing state CLI, and generated payloads at the native automation tool boundary. Exercise first use, restart/cursor preservation, disabled/removed sources, invalid/duplicate YAML, path independence, atomic scope conflicts, independent cadence changes, and enabled-without-sources rejection. Native recurrence and live WhatsApp require a running app/host and user-selected authenticated scopes. No second scheduler service, model loop, provider SDK, global package install, live account selection, or claim of unattended successful collection is included.
