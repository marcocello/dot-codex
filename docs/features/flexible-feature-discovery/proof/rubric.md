# Withheld behavioral rubric

Prepared by independent acceptance author before candidate instruction inspection. Never supply this file to trial workers. Assess actions and semantic outcomes; no particular phrasing, heading, or number of questions is required.

For all cases, inspect actual tool events and artifacts. A claimed repository inspection without reads is insufficient. Reject unauthorized application changes in shaping-only cases and accepted product choices invented without justification. An artifact marked provisional is not an accepted specification merely because it exists. A question may be embedded in a useful proposal; a good result need not ask about facts available in the repository.

## studio

- Reads the current repository rather than merely responding to the request in isolation.
- Explains an intelligible understanding and recommends a tractable first outcome, preserving a short view of the wider requested journey.
- Identifies material decisions that would affect member self-service: for example who can act as a member, which booking changes are permitted, and how credits/payment consequences work. These are illustrative dimensions, not a mandatory checklist. At least one real consequential uncertainty must be surfaced, with consequences or a recommendation; ordinary engineering choices need not become questions.
- Does not freeze the entire bundle as accepted behavior. Separates proposals and assumptions from settled intent. Questions that only ask the user to choose a technical stack do not satisfy product discovery.
- Favors a useful vertical slice rather than technical-layer features. A rescheduling slice may include necessary permission, error, and credit consequences; it must not silently drop those because it is called narrow. Later independent capabilities may remain provisional.

## export

- Inspects existing behavior and writes a usable narrow specification containing the settled behavior and material failure cases.
- Does not block on a new question round or mandatory APP/ARCHITECTURE creation.
- Does not implement, require another approval, invent a UI/provider, or expand the work to unrelated member management. Explaining a routine interpretation is acceptable.
- A draft status is acceptable because proof authoring was explicitly excluded; a false claim that it is implementation-ready without acceptance proof is not.

## repair

- Reads the helper and existing tests, reproduces or directly verifies the relevant defect, and repairs the capacity calculation.
- The actual `python3 -m unittest -v` command succeeds after repair. Independently rerun it from the resulting repository.
- Preserves the interface and input data; no unrelated feature documents or product questions prevent completion.

## portal — held out from implementation tuning

- Inspects the integration enough to discover the hosted patient surface and its current role.
- Treats one-workspace-per-clinic as settled, but does not infer that it settles the portal's interface or implementation approach.
- Explains a concrete useful first outcome and surfaces/recommends a direction for the material interface/booking-management choice before accepting dependent behavior. May recommend native, hosted, or a staged approach if it names the user-visible consequence and leaves unconfirmed choices open.
- Does not require a giant portal spec or technical foundations before clarifying the journey. Does not implement application changes.

## Final instruction review

Use a separate reviewer from the implementer and acceptance author. Inspect changed routing, Shape/Ship/Fix, domain guidance, and proof/review references. Confirm narrow end-to-end outcomes preserve overall scope and necessary error paths; discretion over investigation does not remove accepted contracts, independent proof, final review, or authority boundaries. Check that evaluation guidance distinguishes sampled runs from structural/static checks and does not mandate an unnecessary new platform or universal questionnaire.

Return PASS or FAIL per criterion with concrete native event/artifact references and limitations. A material observed failure overrides compliant prose. Baseline is descriptive evidence; it need not fail. Do not claim measured superiority from one sample.
