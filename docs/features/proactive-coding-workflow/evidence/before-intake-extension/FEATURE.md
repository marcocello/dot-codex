## Accepted behavior

Analysis or specification-only requests stop at their requested deliverable.

Investigate before asking. Ask only when plausible interpretations still produce materially different outcomes that cannot be resolved from the request or current context. Explain the consequence in product language, recommend an option when evidence supports one, and group related unresolved choices concisely. Do not ask users to decide internal process or reconfirm an established permission boundary outside the requested change. Do not infer authorization to broaden roles, mutate production, spend money, or change accepted behavior. A genuinely unresolved consequential choice pauses only dependent work; continue useful work independent of the answer. Never treat silence as an answer.

Distinguish changed intended behavior from a defect; small implementation size alone does not make work a Fix. Explain classification and meaningful assumptions in plain language; do not describe deliberate existing behavior as a bug merely because the user wants it changed.
